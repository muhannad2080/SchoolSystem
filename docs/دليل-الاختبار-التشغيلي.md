# دليل الاختبار التشغيلي لنظام SchoolSystem

## 1. الغرض ونطاق الاختبار

يهدف هذا الدليل إلى توحيد اختبار نظام المدرسة قبل الاستخدام الفعلي. يجب تنفيذ الاختبارات على جهاز Windows يحتوي على Visual Studio 2022 و.NET Framework 4.7.2 وSQL Server، مع أخذ نسخة احتياطية من قاعدة الاختبار قبل البدء.

> لا تُنفّذ اختبارات الحذف أو الاستعادة على قاعدة الإنتاج. استخدم قاعدة اختبار منفصلة أو نسخة مستعادة باسم مثل `SchoolDB_Test`.

## 2. التحضير قبل التشغيل

اجلب آخر نسخة من الفرع الرئيسي، ثم افتح الحل في Visual Studio وابنِ المشروع في وضعي Debug وRelease. شغّل أداة التحقق الثابت من مجلد المشروع:

```powershell
git switch main
git pull --ff-only origin main
python tools\verify_settings_contract.py
```

يجب أن تنجح فحوص العقود والصلاحيات وسجل الأنشطة وRTL/Designer والجاهزية التشغيلية. بعد ذلك حدّث قاعدة الاختبار بملفات الترحيل الموجودة في مجلد `Databass`، وتحقق من أن سلسلة الاتصال تشير إلى قاعدة الاختبار لا إلى قاعدة الإنتاج.

## 3. اختبار تسجيل الدخول والأدوار

أنشئ حسابات اختبار منفصلة للأدوار الإدارية والمالية والأكاديمية وشؤون الطلاب والمستخدم المحدود. لا تستخدم كلمة مرور حقيقية، ولا تضع كلمات المرور في سجل الأنشطة أو لقطات الشاشة.

| الدور | الاختبارات الأساسية | النتيجة المتوقعة |
|---|---|---|
| مدير النظام | فتح لوحة المعلومات والمستخدمين والإعدادات والتقارير، وتغيير صلاحيات مستخدم | تظهر الوحدات المسموح بها فقط، وتُحفظ التغييرات في سجل الأنشطة |
| الشؤون المالية | الرسوم وخطط الرسوم والسندات والمصروفات والرواتب | يستطيع تنفيذ العمليات المالية الممنوحة فقط، ولا يستطيع إدارة المستخدمين أو المواد دون صلاحية |
| الشؤون الأكاديمية | الطلاب والمواد والصفوف والجدول والدرجات والحضور | تظهر الوحدات الأكاديمية الممنوحة فقط، وتُرفض العمليات غير المصرح بها برسالة عربية واضحة |
| شؤون الطلاب | الطلاب والتسجيل والتوزيع والحضور والتقارير المصرح بها | يستطيع إدارة بيانات الطلاب المسموح بها، ولا يرى البيانات المالية دون صلاحية |
| مستخدم محدود | شاشة أو تقرير واحد حسب الصلاحيات | لا تظهر القوائم غير المسموح بها، وتبقى الحماية فعالة حتى عند فتح الشاشة مباشرة |

بعد تعديل صلاحيات أي مستخدم، سجّل الخروج ثم ادخل بالحساب مرة أخرى. اختبر أيضاً محاولة فتح الشاشة من المسار الداخلي أو الزر المباشر؛ يجب أن ترفض الخدمة العملية نفسها، وليس الواجهة فقط.

## 4. اختبار الواجهات وRTL

افتح جميع الشاشات الرئيسية وتحقق من أن النص العربي يبدأ من اليمين، وأن العناوين والحقول والأزرار لا تتداخل عند تغيير حجم النافذة. اختبر التكبير إلى 125% و150%، وتأكد من ظهور النصوص كاملة وعدم اختفاء أزرار الحفظ أو الإلغاء.

| الشاشة | نقاط القبول |
|---|---|
| المستخدمون | الحقول والصلاحيات واضحة، والجدول قابل للتمرير، ورسائل المنع عربية |
| ملف الطالب | ظهور الصورة أو الحالة البديلة، وتبديل تبويب الرسوم حسب الصلاحية |
| الإعدادات | الحقول مرتبة، واختيار مجلد النسخ يعمل، والأزرار لا تتداخل |
| سجل الأنشطة | تحميل وفلترة وتصدير CSV، ومنع التصدير عند غياب الصلاحية |
| السندات | وضوح نوع السند والمبلغ والطباعة، ومنع تعديل السجل التلقائي غير المسموح |
| لوحة المعلومات | العدادات لا تشمل السجلات غير النشطة، والرسوم تعمل دون استثناءات |

## 5. اختبار دورة حياة البيانات

أنشئ سجلاً فعالاً ثم عطّله بالطريقة المعتمدة بدلاً من حذفه متى كان له تاريخ تشغيلي. تحقق من بقاء السجل في التقارير التاريخية عند الحاجة، وعدم ظهوره في قوائم الإدخال الجديدة.

يجب رفض الحالات التالية: إعارة كتاب غير نشط، حفظ درجة لمادة أو طالب غير نشط، إضافة حصة لمعلم أو صف أو مادة غير نشطة، وتسجيل عملية على كيان محذوف أو مرتبط بسجلات مالية. يجب أن تكون الرسالة مفهومة ولا تكشف SQL أو تفاصيل داخلية.

## 6. اختبار سجل الأنشطة

نفّذ إضافة وتعديل وحذفاً آمناً في كل وحدة رئيسية، ثم افتح سجل الأنشطة. يجب تسجيل اسم العملية والوحدة والمستخدم والتاريخ ومعرف الكيان والنتيجة بعد نجاح العملية فقط. تحقق من عدم تسجيل كلمات المرور أو رموز الاتصال أو بيانات حساسة.

اختبر الفلترة بالتاريخ والوحدة والمستخدم، ثم التصدير إلى CSV وافتح الملف ببرنامج Excel للتأكد من سلامة العربية. جرّب التصدير بحساب يفتقد صلاحية العرض؛ يجب رفض العملية وإظهار رسالة عربية.

## 7. اختبار النسخ الاحتياطي والاستعادة

من شاشة الإعدادات، اختبر الاتصال أولاً ثم اختر مجلداً محلياً صالحاً مثل `D:\SchoolSystemBackups`. أنشئ نسخة احتياطية وتحقق من وجود ملف `.bak` وحجمه غير الصفري واسم قاعدة البيانات والتاريخ في اسمه.

جرّب مساراً غير موجود؛ يجب محاولة إنشائه أو استخدام المسار البديل الآمن. جرّب مجلد البرنامج؛ يجب رفضه لحماية ملفات التطبيق. جرّب استعادة النسخة باسم قاعدة جديدة، ثم تحقق من الجداول والبيانات.

لا تختبر خيار استبدال قاعدة موجودة إلا على قاعدة اختبار. بعد الاستعادة، تحقق من عودة قاعدة البيانات إلى وضع `MULTI_USER` حتى لو حدث خطأ، ثم سجّل الدخول إلى التطبيق وتحقق من البيانات والصلاحيات.

## 8. اختبار الأخطاء والتحقق

أدخل قيماً فارغة أو طويلة أو سالبة في الحقول المالية، وأرقاماً مكررة، وتواريخ غير منطقية. يجب منع الحفظ قبل الوصول إلى قاعدة البيانات مع رسالة عربية بجانب سبب الخطأ. افصل الشبكة أو أوقف SQL Server مؤقتاً، ثم افتح شاشة؛ يجب ظهور رسالة مفهومة دون إغلاق التطبيق أو تجمد الواجهة.

راقب سجل الأنشطة وسجل الأخطاء بعد كل حالة فشل للتأكد من عدم تسجيل عملية ناجحة زائفة. يجب إعادة المؤشر والأزرار إلى حالتها الطبيعية بعد انتهاء العملية.

## 9. معايير القبول النهائي

يُقبل الإصدار عندما ينجح البناء في وضعي Debug وRelease، وتنجح أداة التحقق الثابت، وتُفتح جميع الشاشات الأساسية دون صفحة بيضاء أو أخطاء Designer، وتنجح اختبارات الأدوار، وتُرفض العمليات غير المصرح بها من مستوى الخدمة، ويعمل النسخ والاستعادة على قاعدة اختبار، وتبقى قاعدة الإنتاج دون تغيير أثناء الاختبار.

سجّل نتيجة كل اختبار في جدول يتضمن رقم الحالة والتاريخ والحساب والنتيجة والدليل. أي فشل في الصلاحيات أو فقدان بيانات أو فشل استعادة يجب أن يوقف الاعتماد حتى تتم معالجته وإعادة الاختبار.
