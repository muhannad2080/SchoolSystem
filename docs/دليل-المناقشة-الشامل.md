# دليل المناقشة الشامل لنظام SchoolSystem

## 1. تعريف المشروع

نظام **SchoolSystem** هو تطبيق سطح مكتب لإدارة المدرسة، مبني بلغة **C#** باستخدام **Windows Forms** ويستهدف **.NET Framework 4.7.2**. يتصل النظام بقاعدة بيانات **Microsoft SQL Server**، ويغطي العمليات الأكاديمية والإدارية والمالية، مثل الطلاب، التسجيل والقبول، الصفوف والشعب، المعلمين، الحضور، الدرجات، الجداول، الرسوم، المصروفات، السندات، الرواتب، المكتبة، النقل، التقارير، المستخدمين، الإعدادات وسجل الأنشطة.

الاتجاه الأساسي للواجهة هو **RTL** لأن اللغة العربية هي لغة الاستخدام الرئيسية. وفي الوقت نفسه يستطيع النظام عرض البيانات الإنجليزية داخل الحقول والتقارير والطباعة دون أن يخلط بين اتجاه النص واتجاه الشاشة.

> الجملة المختصرة المناسبة للمناقشة: النظام تطبيق مكتبي متعدد الطبقات لإدارة العمليات المدرسية، يفصل واجهة المستخدم عن منطق الأعمال وعن الوصول إلى البيانات، ويستخدم SQL Server كمخزن علائقي مع نظام صلاحيات مركزي ودعم RTL.

## 2. لماذا اختيرت هذه التقنيات؟

اختيرت WinForms لأنها مناسبة لتطبيقات سطح المكتب الإدارية التي تحتوي على نماذج إدخال وجداول وأزرار وتقارير، وتعمل جيدًا في بيئة Windows التي تستخدمها المدارس. استُخدم .NET Framework 4.7.2 لأنه متوافق مع بيئة Visual Studio وقواعد بيانات SQL Server والمكتبات الموجودة في المشروع. استُخدم SQL Server لأنه يوفر المعاملات، القيود، الفهارس، العلاقات، وإدارة البيانات المركزية.

| التقنية | وظيفتها في النظام |
|---|---|
| C# | لغة البرمجة والمنطق والأحداث والخدمات والمستودعات. |
| .NET Framework 4.7.2 | بيئة تشغيل التطبيق ومكتبات WinForms وADO.NET. |
| Windows Forms | بناء النوافذ وعناصر الإدخال والجداول والأزرار. |
| Krypton Toolkit | تحسين الشكل البصري لبعض لوحات وعناصر الواجهة. |
| SQL Server | تخزين البيانات والعلاقات والاستعلامات والمعاملات. |
| ADO.NET | فتح الاتصالات وتنفيذ `SqlCommand` وقراءة `DataTable`. |
| ClosedXML | تصدير الجداول والتقارير إلى Excel. |
| iTextSharp / أدوات التقرير | دعم إخراج PDF والطباعة حسب مسارات التقرير. |
| Git/GitHub | إدارة الإصدارات ومزامنة الفرع `main`. |

## 3. المعمارية البرمجية

المشروع يستخدم **Layered Architecture / N-Tier Architecture**. ليست المعمارية MVC كاملة، لأن WinForms تعتمد على الأحداث وملفات Designer، لكنها تفصل المسؤوليات إلى طبقات واضحة.

```text
المستخدم
   │
   ▼
UI: Forms و UserControls و Designer
   │ يستدعي الخدمات ولا ينفذ قواعد الأعمال مباشرة
   ▼
Services: التحقق والصلاحيات وقواعد العمل والتسجيل
   │
   ▼
DataAccess: Repositories و SQL Parameters و Transactions
   │
   ▼
SQL Server: SchoolDB والجداول والعلاقات والفهارس
```

### 3.1 طبقة العرض UI

توجد في مجلد `UI/`. كل شاشة غالبًا تتكون من ملفين أساسيين:

```text
UI/StudentsForm.cs
UI/StudentsForm.Designer.cs
```

الملف الأول يحتوي على منطق الشاشة والأحداث، مثل حدث الضغط على الحفظ والبحث والتحميل. الملف الثاني ينشئ عناصر الواجهة التي يديرها Visual Studio Designer. لذلك لا ينبغي وضع منطق الأعمال داخل `InitializeComponent`، لأن هذا الجزء خاص بإنشاء العناصر ومواقعها وأحجامها.

الشاشة تنشئ الخدمة الخاصة بها، ثم تستدعيها في أحداث مثل `Load` و`Click`، وتعرض النتيجة داخل `DataGridView` أو عناصر الإدخال.

### 3.2 طبقة الخدمات Services

توجد في مجلد `Services/`. الخدمة هي المكان الذي تُطبق فيه قواعد النظام، مثل:

- التحقق من الصلاحية قبل العملية.
- التأكد من أن المبلغ أكبر من صفر.
- منع تاريخ مستقبلي غير منطقي.
- منع التكرار، مثل تسجيل الطالب مرتين في نفس العام الدراسي.
- منع تعديل أو حذف السند التلقائي.
- تسجيل العملية في سجل الأنشطة.
- استدعاء المستودع المناسب فقط بعد اجتياز التحقق.

أمثلة فعلية: `StudentService`, `EnrollmentService`, `VoucherService`, `FeeService`, `ExpenseService`, `UserService`, `ReportService`.

### 3.3 طبقة الوصول للبيانات DataAccess

توجد في مجلد `DataAccess/`. كل مستودع مسؤول عن مجموعة جداول أو عملية متخصصة. أمثلة:

| المستودع | المسؤولية |
|---|---|
| `StudentRepository` | عمليات الطلاب والاستعلامات الخاصة بهم. |
| `TeacherRepository` | المعلمون وبياناتهم. |
| `EnrollmentRepository` | طلبات التسجيل والقبول. |
| `StudentClassRepository` | توزيع الطلاب على الصفوف والشعب. |
| `VoucherRepository` | إضافة وتعديل وحذف وقراءة السندات وتوليد الرقم. |
| `PartyRepository` | تجميع الطلاب والمعلمين والمستخدمين كأطراف للسندات. |
| `ReportRepository` | الاستعلامات المجمعة للتقارير. |
| `UserRepository` | المستخدمون والأدوار والصلاحيات ومحاولات الدخول. |

المستودعات تستخدم `SqlConnection`, `SqlCommand`, `SqlDataAdapter` و`DataTable`. الاستعلامات تستخدم Parameters بدل دمج النصوص مباشرة، لتقليل خطر SQL Injection.

### 3.4 طبقة Models

توجد في مجلد `Models/`. النموذج يمثل بيانات المجال، مثل `Students`, `Teachers`, `Enrollment`, `Voucher`, `Fee`, `Expense`, `User`. النموذج لا يفترض أن يكون مسؤولًا عن فتح الاتصال بقاعدة البيانات؛ وظيفته حمل البيانات بين الواجهة والخدمة والمستودع.

مثال مسار السند:

```text
حقول VouchersForm
  → GetVoucherFromInputs()
  → Voucher model
  → VoucherService.ValidateVoucher()
  → VoucherRepository.AddVoucher()
  → جدول Vouchers
```

## 4. نقطة بداية تشغيل البرنامج

نقطة البداية هي `Program.cs`. عادةً يتم تفعيل إعدادات Windows Forms ثم إنشاء شاشة الدخول. بعد نجاح الدخول تُنشأ الشاشة الرئيسية.

التدفق العام:

```text
Main()
  → تهيئة Windows Forms
  → إنشاء LoginForm
  → المستخدم يكتب اسم المستخدم وكلمة المرور
  → UserService يتحقق من البيانات
  → CurrentUser.Set(user)
  → فتح MainForm
```

إذا أغلق المستخدم الجلسة أو اختار الخروج، يجب استدعاء `CurrentUser.Clear()` ثم العودة إلى شاشة الدخول بدل إغلاق التطبيق بالكامل. هذا يفصل الجلسة القديمة عن الجلسة الجديدة.

## 5. الاتصال بقاعدة البيانات

يوجد اتصال مركزي في `DataAccess/DbConnection.cs`. بدل أن تكتب كل شاشة سلسلة الاتصال بنفسها، تستدعي المستودعات:

```csharp
using (SqlConnection con = DbConnection.GetConnection())
{
    using (SqlCommand cmd = new SqlCommand(query, con))
    {
        con.Open();
        // تنفيذ الاستعلام
    }
}
```

سلسلة الاتصال موجودة في `App.config` تحت الاسم `SchoolDBConnection`. في النسخة الحالية تُستخدم قاعدة `SchoolDB` على SQL Server مع Windows Authentication. عند نقل المشروع إلى جهاز آخر يجب تغيير اسم الخادم في `App.config` أو إعداد اتصال مناسب.

### لماذا استخدمنا `using`؟

كتلة `using` تضمن استدعاء `Dispose` حتى عند حدوث خطأ. هذا يغلق الاتصال والأمر ويمنع تسرب الموارد أو تراكم الاتصالات المفتوحة.

### لماذا استخدمنا Parameters؟

الاستعلام غير الآمن يكون مثل:

```csharp
string query = "SELECT * FROM Users WHERE UserName = '" + name + "'";
```

هذا يسمح بإدخال نص يغير معنى SQL. أما الأسلوب المستخدم فهو:

```csharp
SqlCommand cmd = new SqlCommand(
    "SELECT * FROM Users WHERE UserName = @UserName", con);
cmd.Parameters.AddWithValue("@UserName", name);
```

هنا تُرسل القيمة كبيانات وليس كجزء من كود SQL.

## 6. تسجيل الدخول والأمان والصلاحيات

### 6.1 `PasswordHasher`

كلمات المرور لا ينبغي تخزينها كنص صريح. `Security/PasswordHasher.cs` مسؤول عن إنشاء قيمة مشتقة من كلمة المرور والتحقق منها عند الدخول. الفكرة هي مقارنة نتيجة الهاش لكلمة المرور المدخلة بالقيمة المخزنة، وليس مقارنة كلمة المرور الخام بقاعدة البيانات.

### 6.2 `CurrentUser`

`Security/CurrentUser.cs` يحتفظ بجلسة المستخدم الحالية في الذاكرة. أهم أدواره:

| الدالة | الوظيفة |
|---|---|
| `Set(User user)` | إنشاء الجلسة بعد نجاح الدخول وتطبيع الدور والصلاحيات. |
| `Clear()` | إنهاء الجلسة الحالية. |
| `IsLoggedIn` | معرفة هل توجد جلسة. |
| `IsAdmin()` | التحقق من دور مدير النظام. |
| `HasPermission(key)` | فحص صلاحية محددة. |
| `DemandPermission(key, message)` | فحص الصلاحية ورمي `UnauthorizedAccessException` إذا لم توجد. |
| `DemandAny(message, keys)` | السماح إذا امتلك المستخدم واحدة من الصلاحيات. |

### 6.3 `PermissionKeys`

`Security/PermissionKeys.cs` هو القاموس المركزي لأسماء الصلاحيات. أمثلة:

```text
Students.View
Students.Manage
Enrollment.Manage
ClassAssignment.Manage
Teachers.Manage
Fees.Manage
Vouchers.Manage
Expenses.Manage
Reports.View
Users.Manage
AuditLogs.View
Settings.Manage
```

استخدام ثابت مركزي أفضل من كتابة النصوص في كل ملف، لأنه يقلل أخطاء الكتابة ويوحد النظام.

### 6.4 كيف تعمل الصلاحية؟

عند تسجيل الدخول، تُحمّل بيانات المستخدم ودوره وصلاحياته. `CurrentUser.Set` يطبع اسم الدور ويطبع الصلاحيات إلى مجموعة مفهومة. إذا كان المستخدم مدير النظام، تُشتق صلاحياته الافتراضية من `PermissionKeys`، فلا تختفي الوحدات بسبب قيمة قديمة أو ناقصة في عمود الصلاحيات.

ثم توجد طبقتان للحماية:

1. الواجهة قد تخفي أو تعطل الزر الذي لا يملك المستخدم صلاحيته.
2. الخدمة نفسها تفحص الصلاحية قبل أي تعديل، حتى لا يستطيع المستخدم تجاوز الواجهة باستدعاء العملية من مسار آخر.

> الحماية الحقيقية يجب أن تكون في الخدمة، وليس في إخفاء الزر فقط.

## 7. القفل بعد محاولات الدخول الفاشلة

النظام يتعامل مع محاولة الدخول الفاشلة على مستوى خدمة المستخدم. المستخدم العادي يمكن قفل حسابه بعد عدد محاولات متتالية خاطئة، بينما مدير النظام مستثنى من هذا السلوك حتى لا يتم قفل الحساب الإداري الرئيسي. عند القفل تُعرض رسالة واضحة للمستخدم، ويمكن تسجيل الحدث وإرسال تنبيه وفق إعدادات البريد الموجودة في الخدمة المخصصة لذلك.

القاعدة الأمنية المهمة هي أن كلمة المرور الصحيحة لا تتجاوز حالة الحساب غير النشط؛ يجب أولًا أن يكون الحساب فعالًا، ثم تكون كلمة المرور صحيحة.

## 8. دورة حياة شاشة نموذجية

كل شاشة CRUD تقريبًا تتبع هذا التسلسل:

```text
Constructor
  → InitializeComponent()
  → تطبيق النمط العام
  → إنشاء الخدمة
  → ربط الأحداث

Load event
  → فحص الصلاحية
  → تحميل القوائم المرجعية
  → تحميل البيانات من الخدمة
  → ربط DataTable مع DataGridView

New/Clear
  → مسح الحقول
  → ضبط القيم الافتراضية
  → وضع المؤشر في أول حقل

Save
  → قراءة الحقول إلى Model
  → ValidateInputs في الواجهة
  → استدعاء Service
  → تحديث الجدول
  → رسالة نجاح أو خطأ

Grid CellClick
  → قراءة الصف
  → تعبئة الحقول
  → تحديد المعرف
  → تفعيل التعديل والحذف حسب الحالة
```

## 9. شرح شاشة الطلاب

`UI/StudentsForm.cs` مسؤول عن إدخال الطلاب وعرضهم وتعديلهم وحذفهم والبحث والتصدير. عند الحفظ تُقرأ الحقول إلى نموذج الطالب، ثم تمر العملية على `StudentService` الذي يتحقق من البيانات والتكرار، ثم يستدعي `StudentRepository`.

الرقم الداخلي أو رقم الطالب يمكن أن يتولد تلقائيًا حسب قواعد المشروع. لا ينبغي للمستخدم إدخال المعرف الداخلي يدويًا؛ المعرف قاعدة بيانات، بينما الرقم الظاهر للطالب رقم أعمال قابل للعرض.

الأزرار المعتادة:

| الزر | ما يحدث داخليًا |
|---|---|
| إضافة/حفظ | قراءة الحقول، التحقق، استدعاء `AddStudent`، ثم إعادة التحميل. |
| تعديل | استخدام معرف الصف المحدد واستدعاء `UpdateStudent`. |
| حذف | طلب تأكيد، فحص الصلاحية، استدعاء `DeleteStudent`. |
| بحث | تطبيق فلترة فورية أو تحميل نتائج مطابقة. |
| تصدير | إرسال `DataTable` إلى مساعد التقرير لإخراج Excel أو PDF. |
| تنظيف | تصفير المعرف ومسح الحقول وإعادة المؤشر لأول حقل. |

## 10. شرح التسجيل والقبول

الشاشة تجمع بيانات الطالب وتحدد الصف والعام الدراسي والشعبة. العام الدراسي لا ينبغي كتابته بشكل عشوائي؛ يُحسب وفق تاريخ العملية ودورة المدرسة المعتمدة، وهي دورة أغسطس إلى يوليو في منطق المشروع.

عند تغيير الصف، تُحمّل الشعب المرتبطة بالصف والعام الدراسي. الخدمة `StudentClassService` تفحص صلاحية توزيع الطلاب. إذا ظهرت رسالة `UnauthorizedAccessException` فهذا يعني أن المستخدم لا يمتلك `ClassAssignment.Manage` أو أن دوره لم تُمنح له الصلاحية.

قبل حفظ التسجيل، تتحقق الخدمة من عدم وجود تسجيل سابق لنفس الطالب في نفس العام الدراسي. لذلك رسالة "هذا الطالب مسجل بالفعل في هذا العام الدراسي" هي حماية من التكرار وليست خطأ في قاعدة البيانات.

## 11. شرح شاشة السندات المالية

الشاشة `UI/VouchersForm.cs` تدير سندي **قبض** و**صرف**. أهم المكونات:

- `VoucherService` لتطبيق قواعد السند.
- `VoucherRepository` لتنفيذ SQL.
- `PartyService` لتحميل الأطراف.
- `PartyRepository` لتوحيد الطلاب والمعلمين والمستخدمين في قائمة واحدة.
- `txtVoucherNumber` لعرض الرقم التلقائي للقراءة فقط.
- `cmbPartyName` لقائمة الطرف القابلة للبحث.

### 11.1 توليد رقم السند

عند إنشاء سند جديد، تنفذ الشاشة `ClearInputs` ثم تختار نوع السند وتستدعي `SetNextVoucherNumber`. هذه الدالة تستدعي:

```csharp
voucherService.GenerateVoucherNumber(cmbVoucherType.Text.Trim())
```

الخدمة تفحص `Vouchers.Manage` ثم تستدعي المستودع. المستودع يستخدم بادئة `REC` للقبض و`PAY` للصرف، مع العام ورقم تسلسلي مبدئي. عند الحفظ، إذا احتاج السند رقمًا نهائيًا، يبني المستودع رقمًا يعتمد على `VoucherID` الذي أعادته قاعدة البيانات.

### 11.2 قائمة الطرف

`PartyRepository` ينفذ اتحادًا `UNION ALL` بين:

- الطلاب النشطين من `Students`.
- المعلمين النشطين من `Teachers`.
- المستخدمين النشطين غير مدير النظام من `Users` باعتبارهم موظفين أو أطرافًا إدارية.

كل عنصر يعرض اسمًا مقروءًا، ويحتفظ بقيمة داخلية مثل:

```text
STUDENT:15
TEACHER:4
STAFF:7
```

هذا الأسلوب يسمح معرفة نوع الطرف ومعرفه مستقبلًا دون خلط الاسم فقط.

### 11.3 الفرق بين القبض والصرف

سند القبض يمثل أموالًا تدخل إلى المدرسة، مثل رسوم طالب. سند الصرف يمثل أموالًا تخرج من المدرسة، مثل مصروف أو دفع لمورد أو موظف. النوع يحدد البادئة، وطبيعة الحركة المالية، والمرجع المتوقع.

| الحالة | النوع | المرجع |
|---|---|---|
| دفع رسوم طالب | قبض | رسوم + رقم الرسوم |
| تسوية مصروف | صرف | مصروفات + رقم المصروف |
| حركة عامة | قبض أو صرف | عام بدون رقم مرجع |

`ValidateVoucher` يمنع المبلغ غير الموجب، الطرف الفارغ، البيان الفارغ، التاريخ المستقبلي، طريقة الدفع الفارغة، والمرجع غير المتسق. إذا اختير نوع مرجع مرتبط يجب إدخال رقم مرجع، وإذا كان النوع عامًا فلا يجوز إدخال رقم.

### 11.4 منع تكرار السندات

قبل الإدراج داخل معاملة SQL، يتحقق `VoucherRepository` من عدم وجود رقم السند مسبقًا. كما يمنع إنشاء سند تلقائي آخر لنفس نوع المرجع ورقمه. السند الذي يحمل `IsAutoGenerated = true` لا يسمح النظام بتعديله أو حذفه لأنه ناتج عن عملية محاسبية أخرى.

### 11.5 أزرار السندات

| الزر | الوظيفة |
|---|---|
| سند قبض جديد | تنظيف الحقول، اختيار قبض، توليد رقم، وضع المؤشر في المبلغ. |
| سند صرف جديد | تنظيف الحقول، اختيار صرف، توليد رقم، وضع المؤشر في المبلغ. |
| إضافة | التحقق ثم استدعاء `VoucherService.AddVoucher`. |
| تعديل | تعديل السند اليدوي فقط. |
| حذف | حذف السند اليدوي فقط بعد التأكيد. |
| معاينة | تجهيز `PrintDocument` وفتح `PrintPreviewDialog`. |
| طباعة | إرسال المستند إلى الطابعة. |
| تصدير Excel | تحويل الصفوف المرئية إلى `DataTable` واستدعاء `ReportOutputHelper`. |
| بحث | تطبيق فلترة على رقم السند أو الطرف أو البيان. |
| تنظيف | إعادة الشاشة إلى وضع سند جديد مع رقم جديد. |

## 12. التقارير والطباعة والتصدير

التقرير يبدأ غالبًا من `ReportCenterForm`، ويُمرر طلب التقرير إلى `ReportService` ثم `ReportRepository`. بعد وصول البيانات تُعرض في `DataGridView` أو تُرسل إلى `ReportOutputHelper`.

`ReportOutputHelper` مسؤول عن تنسيق العنوان، الأعمدة، اتجاه النص، وتصدير Excel. الطباعة تستخدم `PrintDocument` و`PrintPage`، حيث تُرسم الحقول يدويًا باستخدام `Graphics` و`StringFormat` بمحاذاة RTL.

القاعدة المهمة في التقرير هي فصل **مصدر البيانات** عن **إخراج البيانات**. الاستعلام لا يجب أن يعرف كيف ستتم الطباعة، والطباعة لا يجب أن تكتب SQL.

## 16. الأخطاء الشائعة وكيفية تفسيرها

| الرسالة | التفسير |
|---|---|
| `UnauthorizedAccessException` | المستخدم لا يملك الصلاحية المطلوبة أو لم تُحمّل جلسة صحيحة. |
| `هذا الطالب مسجل بالفعل` | يوجد تسجيل لنفس الطالب في العام الدراسي نفسه. |
| `Invalid object name` | الاتصال بقاعدة خاطئة، غالبًا `master` بدل `SchoolDB`، أو لم تُطبق الترحيلات. |
| `Invalid column name` | سكربت البيانات يفترض عمودًا غير موجود في نسخة المخطط الحالية. |
| `Cannot insert NULL into Section` | الإدخال لم يمرر الشعبة، ويجب اختيار شعبة ثابتة مرتبطة بالصف. |
| `FileNotFoundException System.ValueTuple` | مشكلة حزم أو نسخ DLL في جهاز Windows، وتعالج باستعادة NuGet والـ binding redirects. |
| اختفاء زر | غالبًا خاصية `Visible`, `Enabled`, `Dock`, أو ترتيب عناصر Designer، وليس بالضرورة خطأ في حدث الزر. |

## 17. كيف أشرح ربط الواجهة بالكلاس؟

عند سؤال الدكتور: "كيف ربطت الواجهة بالكلاس؟" تكون الإجابة:

الواجهة لا ترث من الخدمة، بل تحتوي على كائن خدمة كحقل خاص، مثل:

```csharp
private readonly VoucherService voucherService = new VoucherService();
```

عند الضغط على زر الحفظ، يقرأ الحدث قيم عناصر الإدخال ويبني Model، ثم يمرره إلى الخدمة. الخدمة تتحقق من الصلاحية والقيم، ثم تستدعي Repository. بعد عودة النتيجة تعرض الواجهة رسالة وتعيد تحميل الجدول. هذا يسمى **Composition** ويفصل الواجهة عن تفاصيل SQL.

## 18. كيف أشرح الفرق بين Model وService وRepository؟

- **Model:** شكل البيانات، مثل خصائص `VoucherID`, `Amount`, `PartyName`.
- **Service:** ماذا يُسمح أن يحدث، مثل منع مبلغ صفر أو تعديل سند تلقائي.
- **Repository:** كيف تُقرأ أو تُكتب البيانات فعليًا في SQL Server.
- **Form:** كيف يدخل المستخدم البيانات ويرى النتيجة.

مثال واحد يوضح الفرق:

```text
Voucher model = البيانات
VoucherService = القواعد والصلاحيات
VoucherRepository = SQL والإدراج
VouchersForm = الحقول والأزرار والرسائل
```

## 19. القيود الحالية التي يجب ذكرها بصدق

التطبيق WinForms مكتبي، لذلك يحتاج جهاز Windows وVisual Studio أو ملف تشغيل منشور، ولا يمكن اختبار عرض النوافذ فعليًا على Linux. قاعدة SQL Server يجب أن تكون متاحة من جهاز العميل. بعض مكتبات Excel وPDF تعتمد على توافق DLL وNuGet، لذلك يجب استعادة الحزم قبل البناء. كما أن صلاحيات SQL Server وWindows Authentication جزء من إعداد البيئة وليست مخزنة داخل C#.

## 20. جواب ختامي جاهز للمناقشة

> بنيت النظام على معمارية متعددة الطبقات. الواجهات في UI مسؤولة عن العرض والأحداث فقط، والخدمات في Services مسؤولة عن التحقق والصلاحيات وقواعد الأعمال، والمستودعات في DataAccess مسؤولة عن SQL Server باستخدام ADO.NET وParameters، والنماذج في Models تحمل البيانات بين الطبقات. استخدمت `CurrentUser` و`PermissionKeys` لتطبيق RBAC، و`PasswordHasher` لحماية كلمات المرور، و`using` لإدارة الاتصالات، وSQL Transactions للعمليات الحساسة مثل السندات. صممت الواجهات RTL، وأضفت التحقق في الواجهة والخدمة معًا، لأن إخفاء الزر وحده لا يكفي للحماية."
