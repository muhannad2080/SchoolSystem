# دليل مناقشة مشروع SchoolSystem

## 1. التعريف العام بالنظام

نظام **SchoolSystem** هو تطبيق مكتبي لإدارة العمليات المدرسية، بُني باستخدام **C# وWindows Forms** ويستهدف بيئة **.NET Framework 4.7.2**. يتعامل النظام مع الطلاب، المعلمين، التسجيل والقبول، الصفوف والشعب والقاعات، الحضور، الدرجات، المكتبة، النقل، الرسوم والمصروفات والرواتب والسندات والتقارير والمستخدمين.

صُمم النظام ليكون قابلًا للصيانة والتوسع؛ فالواجهة لا تتصل بقاعدة البيانات مباشرة، بل تمر العملية عبر خدمة أعمال ثم مستودع بيانات. كما أضيفت طبقة أمنية مركزية للصلاحيات، وطبقة تسجيل تدقيق للعمليات الحساسة، وقواعد تحقق تمنع التكرار وتحافظ على النزاهة المالية.

## 2. المعمارية المستخدمة

المعمارية الأساسية هي **Repository/Service Pattern** مع تطبيق مبادئ فصل المسؤوليات. تتكون العملية النموذجية من أربعة أجزاء: واجهة المستخدم، خدمة الأعمال، مستودع البيانات، ونموذج البيانات.

| الطبقة | أمثلة من المشروع | المسؤولية |
|---|---|---|
| واجهة المستخدم UI | `StudentsForm`, `EnrollmentForm`, `VouchersForm`, `ReportCenterForm` | استقبال الإدخال، عرض البيانات، إظهار رسائل النجاح والخطأ |
| الخدمات Services | `StudentService`, `EnrollmentService`, `VoucherService` | التحقق، قواعد العمل، الصلاحيات، تسجيل التدقيق |
| الوصول للبيانات DataAccess | `StudentRepository`, `EnrollmentRepository`, `DbConnection` | تنفيذ الاستعلامات والتعامل مع SQL Server |
| النماذج Models | `Students`, `Enrollment`, `Voucher`, `User` | تمثيل البيانات بين الطبقات |
| الأمن Security | `CurrentUser`, `PermissionKeys` | الجلسة الحالية، الصلاحيات، أدوار المستخدمين |
| المساعدات Helpers | `UIHelper` | RTL، التحقق، فلاتر البحث الآمنة، تنسيق الواجهة |

تستدعي الواجهة الخدمة، وتتحقق الخدمة من صلاحية المستخدم ومن صحة البيانات، ثم تستدعي المستودع. بهذه الطريقة لا تحتوي الواجهة على منطق SQL أو قواعد مالية، ولا يستطيع استدعاء مباشر من الواجهة تجاوز الحماية الموجودة في الخدمة.

## 3. الاتصال بقاعدة البيانات

يُدار الاتصال من خلال `DataAccess/DbConnection.cs`. تُقرأ معلومات الاتصال من `App.config`، ثم تستخدم المستودعات اتصالًا موحدًا لتنفيذ أوامر SQL. تُستخدم الاستعلامات ذات المعاملات `Parameters` لتقليل مخاطر حقن SQL، ويجري فتح الاتصال وتنظيفه داخل نطاق العملية.

في العمليات المركبة، مثل حذف معلم له سجلات مرتبطة أو استعادة قاعدة البيانات، تُستخدم المعاملات. مثال ذلك `TeacherRepository` الذي يتحقق من الاعتماديات التاريخية داخل معاملة بمستوى عزل `Serializable`، ثم يمنع الحذف أو يحوله إلى تعطيل آمن عند وجود سجلات مرتبطة.

## 4. دورة تنفيذ زر الحفظ

عند ضغط زر الحفظ في أي واجهة تحدث المراحل التالية:

1. يقرأ الحدث قيم عناصر الإدخال.
2. تطبق `UIHelper` قواعد التحقق والتطبيع مثل إزالة المسافات الزائدة، فحص البريد والهاتف، والتحقق من الأرقام والمبالغ.
3. تستدعي الواجهة دالة الخدمة المناسبة.
4. تتحقق الخدمة من الصلاحية باستخدام `CurrentUser.DemandAction`.
5. تطبق الخدمة قواعد العمل مثل منع التكرار والتحقق من العلاقات.
6. ينفذ المستودع العملية في SQL Server.
7. تُسجل العملية في `AuditLogService` عند نجاح التغيير.
8. تُحدّث الشبكة وتظهر رسالة للمستخدم.

هذا التسلسل يمنع الاعتماد على الواجهة وحدها؛ حتى لو استُدعيت الخدمة من مكان آخر تبقى الصلاحية والتحقق مطبقين.

## 5. نظام الصلاحيات RBAC

يعتمد النظام على **Role-Based Access Control** مع صلاحيات إجرائية دقيقة. لا تقتصر الصلاحية على فتح الشاشة، بل يمكن فصلها إلى عرض وإضافة وتعديل وحذف وطباعة وتصدير وإدارة.

تُعرّف المفاتيح المركزية في `Security/PermissionKeys.cs`. ويُستخدم الاستدعاء التالي داخل الخدمات:

```csharp
CurrentUser.DemandAction("Students", "Add", "ليس لديك صلاحية إضافة الطلاب.");
```

يعني ذلك أن صلاحية فتح شاشة الطلاب لا تمنح تلقائيًا صلاحية إضافة طالب. بعد منح الصلاحيات من واجهة المستخدم تُحفظ القيم في قاعدة البيانات، وعند تسجيل الدخول يعاد تحميلها إلى الجلسة الحالية. وتُعطى الأولوية للتعديلات اليدوية على الصلاحيات الافتراضية للدور، بينما يحتفظ مدير النظام بصلاحياته النظامية المحمية.

| مستوى الصلاحية | الاستخدام |
|---|---|
| View | قراءة الشاشة والبيانات |
| Add | إنشاء سجل جديد |
| Edit | تعديل سجل موجود |
| Delete | حذف أو تعطيل سجل وفق قواعد الحماية |
| Print | طباعة التقرير أو البطاقة |
| Export | تصدير البيانات |
| Manage | صلاحية إدارية واسعة للوحدة |

## 6. تسجيل الدخول وقفل الحساب

توجد معالجة مركزية في `UserService.Authenticate`. تُطبّع الأرقام عند الحاجة، ولا تُجرى عملية `Trim` على كلمة المرور حتى لا تتغير كلمة مرور صحيحة تحتوي على مسافات. عند فشل الدخول تُسجل المحاولة، وبعد المحاولة الثالثة يُعطل حساب المستخدم غير المدير. تُرسل الإشعارات بصورة غير متزامنة، وتُعزل أخطاء البريد حتى لا تمنع تسجيل نتيجة القفل في قاعدة البيانات.

كلمات المرور لا تُحفظ كنص صريح، بل تستخدم آلية التجزئة والملح الموجودة في `PasswordHasher`. كما تُحفظ عمليات إعادة التعيين في سجل التدقيق دون تسجيل كلمة المرور نفسها.

## 7. النزاهة ومنع التكرار

تطبق قواعد منع التكرار في مستويين. المستوى الأول داخل الخدمة برسائل واضحة قبل الحفظ، مثل منع استخدام رقم الهوية أو هاتف الطالب لطالب آخر. والمستوى الثاني داخل قاعدة البيانات بواسطة القيود والفهارس التي أضيفت في `Migration_AddDuplicatePreventionConstraints.sql`.

في التسجيل والقبول يُطابق الطالب مع العام الدراسي، ويُولد العام الدراسي حسب تاريخ الطلب. لذلك لا يمكن تسجيل الطالب نفسه مرتين في العام نفسه، حتى لو حاول المستخدم تكرار الطلب من شاشة مختلفة.

## 8. العمليات المالية

تُدار الرسوم والمصروفات والرواتب والسندات عبر خدمات مستقلة. اختيار الطرف في السند إلزامي ومن قائمة منسدلة، ويولد رقم السند تلقائيًا. لا يُسمح بحذف رسم سُجلت عليه دفعة، ولا حذف مصروف مرتبط بسند، وتستخدم التسويات سندات تلقائية عند الحاجة.

القاعدة المحاسبية المهمة هي أن الحذف لا يزيل التاريخ المالي القابل للتدقيق؛ بل تمنع الخدمة الحذف عندما تكون هناك حركة مرتبطة، أو تستخدم التعطيل المنطقي عند تصميم الوحدة لذلك. كل تغيير ناجح يسجل نوع العملية والكيان والمعرف والتفاصيل.

## 9. البحث والتقارير

تستخدم الواجهات حدث `TextChanged` للبحث الفوري. لذلك يبدأ البحث من أول حرف أو رقم دون انتظار اكتمال الكلمة. أضيفت دالة مركزية في `Helpers/UIHelper.cs` لبناء فلتر `DataView` آمن، بحيث تُحمى القيم من رموز الفلتر وتُبحث الكلمات المتعددة عبر عدة أعمدة.

يدعم مركز التقارير الفلاتر ومسحها والتصدير بصيغة CSV مع **UTF-8 BOM** حتى تظهر العربية بصورة صحيحة في البرامج الداعمة. كما توجد مسارات منفصلة للتقارير والطباعة والتصدير، وتتحقق الواجهة من صلاحية الطباعة أو التصدير قبل التنفيذ.

## 10. RTL وتصميم الواجهات

تستخدم الواجهات خصائص RTL الموحدة، ويُطبق الإعداد على النوافذ وملفات Designer. رُوجعت 26 شاشة للتحقق من وجود `InitializeComponent` واحد، وخصائص الاتجاه، وعدم وجود عناصر مخفية غير مقصودة. تستخدم الأزرار ترتيبًا واضحًا، وتُثبت العناصر بواسطة `Dock` و`Anchor` حيث يلزم لتقليل التداخل عند تغيير حجم النافذة.

## 11. النسخ الاحتياطي والاستعادة

تنفذ `DatabaseBackupService` التحقق من المسار وقاعدة البيانات قبل إنشاء النسخة. يُمنع استخدام مجلد التطبيق نفسه بطريقة قد تسبب الكتابة فوق ملفات النظام. أثناء الاستعادة تُستخدم حماية المستخدم الواحد عند الحاجة، ثم تعاد القاعدة إلى وضع المستخدمين المتعددين في مسار تنظيف منظم. يجب تنفيذ هذه العملية على نسخة اختبارية قبل قاعدة الإنتاج.

## 13. أسئلة متوقعة وإجاباتها

**لماذا استخدمت Service وRepository؟** لأن فصل قواعد العمل عن SQL وعن الواجهة يجعل الاختبار والصيانة أسهل، ويمنع تكرار منطق الصلاحيات والتحقق.

**كيف تمنع تجاوز الصلاحيات؟** تتحقق الواجهة لتحسين تجربة المستخدم، لكن التحقق الحاسم موجود داخل الخدمات قبل كل عملية تغيير، لذلك لا تعتمد الحماية على إخفاء الزر فقط.

**كيف تمنع التكرار؟** تستخدم الخدمة تحققًا مبكرًا برسالة واضحة، وتستخدم قاعدة البيانات قيودًا تمنع التكرار حتى في حال وجود مسار إدخال آخر.

**كيف تحافظ على السجل المالي؟** تمنع حذف السجل المرتبط بحركة مالية، وتستخدم التعطيل أو التسوية بدل إزالة التاريخ المحاسبي.

**كيف يعمل البحث متعدد الكلمات؟** يقرأ الحقل مع كل تغيير، يقسم النص إلى كلمات، يحمي كل كلمة، ثم يبني شروطًا تجعل كل الكلمات مطلوبة عبر أعمدة البحث المحددة.

**ما حدود الاختبار الحالي؟** اجتازت فحوص الكود والعقود الساكنة، أما البناء والتشغيل الفعلي لـWinForms و.NET Framework 4.7.2 فيجب تنفيذه على Windows داخل Visual Studio مع SQL Server.
