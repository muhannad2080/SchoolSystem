# سجل تنفيذ سيناريو النظام الكامل

## الحالة

هذا الملف هو سجل متابعة تنفيذ السيناريو التشغيلي الكامل. تم إنشاء الجرد الأولي للواجهات والخدمات والصلاحيات ومسارات الحفظ قبل تعديل أي وظيفة.

## قاعدة التحقق المتسلسلة

`طالب → تسجيل → قبول → توزيع → خطة رسوم → رسوم → سداد → سند`

`صف + شعبة + مادة + معلم + قاعة + وقت → جدول`

`موظف + عقد ساري → راتب`

## نتائج الفحص الأولي

تم التأكد من وجود ملفات الواجهات والخدمات والمستودعات الأساسية في المشروع، ومن وجود مسارات حماية للصلاحيات ورسائل أخطاء عربية في عدد كبير من العمليات. كما تم تحديد أن التحقق الفعلي من قاعدة البيانات والبناء النهائي يحتاج إلى بيئة Windows/SQL Server متصلة بقاعدة الاختبار.

## منهج التنفيذ التالي

1. مراجعة كل وحدة على مستوى Model ثم Repository ثم Service ثم Form.
2. إضافة أو تشديد قيود التكرار والعلاقات دون حذف بيانات صحيحة.
3. اختبار كل عملية نجاح وفشل على مستوى الكود، ثم تنفيذ اختبار قبول على Windows.
4. تحديث هذا الملف بعد كل مرحلة مع الملفات والاختبارات والنتائج.

## ملاحظة مهمة

نجاح الفحص النصي أو البناء لا يثبت وحده اكتمال النظام. يجب إعادة فتح الشاشة وفحص النتيجة من قاعدة البيانات وتنفيذ الاختبار السلبي المقابل لكل قاعدة عمل.

## تحديث تنفيذ المرحلة: قيود التكرار الأكاديمية والمالية

تمت إضافة حماية على مستوى SQL Server داخل `Migration_HardenStudentFinanceWorkflow.sql` لمنع تكرار التسجيل للطالب في العام الدراسي نفسه بعد تطبيع صيغ العام (`2026/2027` و`2026-2027`) عبر القيد `UX_Enrollments_StudentYear`. كما تمت إضافة حماية تمنع تكرار رسوم خطة واحدة للطالب والعام نفسه عبر القيد `UX_Fees_StudentYearPlan`، مع عدم حذف أي بيانات قائمة؛ فإذا وجدت بيانات مكررة فلن ينشئ الترحيل القيد وسيبقى الأمر بحاجة إلى مراجعة يدوية.

تم توحيد فحص حالة القبول في استعلام التحقق ليقبل `مقبول` و`Accepted`. يجب بعد تشغيل الترحيل تنفيذ فحوصات: تكرار التسجيل، تكرار الرسوم المرتبطة بخطة، توزيع بلا تسجيل مقبول، رسوم بلا طالب، ورسوم تشير إلى خطة غير موجودة. لا تعتبر المرحلة ناجحة إلا إذا كانت نتائج الفحوصات صفرية أو موثقة ومراجعة.

## تحديث تنفيذ المرحلة: الحضور والدرجات

تمت إضافة حماية SQL Server قابلة لإعادة التشغيل لمنع تكرار حضور الطالب في اليوم التقويمي نفسه، ومنع تكرار حضور المعلم في اليوم نفسه، عبر أعمدة محسوبة تتجاهل وقت التسجيل. كما تمت إضافة قيد يمنع تكرار درجة الطالب للمادة نفسها والعام نفسه والفصل الدراسي نفسه، مع تطبيع صيغ العام الدراسي.

تظل عملية تعديل الدرجة الموجودة مسموحة لتصحيحها، بينما يمنع القيد إنشاء سجل ثانٍ لنفس الطالب والمادة والعام والفصل. وإذا كانت بيانات قديمة مكررة، لا يحذف الترحيل شيئاً ولا ينشئ القيد حتى تتم مراجعة التكرارات.

## تحديث تنفيذ المرحلة: الجدول الدراسي وربط الدرجات

تتحقق عملية حفظ الجدول من تعارض المعلم والشعبة والقاعة ضمن العام والفصل واليوم والفترة الزمنية، مع استثناء السجل الجاري تعديله. تمت إضافة تحقق صريح قبل حفظ الدرجة للتأكد من وجود توزيع فعلي للطالب في `StudentClasses` يطابق الصف والشعبة والعام المحدد، كما أصبحت قائمة إدخال الدرجات تعتمد على الطلاب الموزعين فعلياً بدلاً من بيانات الصف الثابتة في سجل الطالب.

اختبارات القبول: محاولة حفظ درجة لطالب غير موزع يجب أن تُرفض برسالة عربية؛ محاولة حفظ درجة للصف أو الشعبة الخطأ يجب أن تُرفض؛ حفظ الدرجة نفسها مرة ثانية يجب أن يعدّل السجل؛ وإضافة حصة لمعلم أو شعبة أو قاعة متعارضة زمنياً يجب أن تُرفض.

## تحديث تنفيذ المرحلة: التقارير وعزل العام

تم تحديث تقرير الرسوم ليعرض الصف والشعبة من جدول `StudentClasses` وفق العام الدراسي الموجود في سجل الرسم، بدلاً من الاعتماد على `Students.ClassID` و`Students.Section`. كما أصبحت فلاتر الصف والشعبة في التقرير تطبق على التوزيع السنوي الفعلي.

اختبار القبول: طالب موزع في الصف الأول الثانوي والشعبة A في العام 2026/2027 وله رسوم مرتبطة بخطة ذلك الصف؛ عند اختيار التقرير لنفس العام والصف والشعبة يظهر السجل مع الصف والشعبة الصحيحين. عند تغيير العام لا يظهر السجل إلا إذا كانت له رسوم وتوزيع في العام الجديد. يجب أيضاً اختبار التصدير والطباعة بعد ظهور النتائج الصحيحة.

تم التحقق النصي بواسطة `git diff --check`، ويجب تنفيذ اختبار SQL والبناء النهائي على Windows/SQL Server.

## المرحلة المحاسبية: الرواتب والسندات

- تم ربط الراتب الذي يحمل تاريخ صرف بسند صرف تلقائي من نوع `صرف` ومرجع `رواتب`، ورقم المرجع هو `PayrollID`.
- السند يستخدم صافي الراتب بعد احتساب الأساسي والبدلات والخصومات.
- إعادة حفظ الراتب المدفوع لا تنشئ سنداً تلقائياً مكرراً بسبب حماية `VoucherRepository` للمرجع والنوع.
- طريقة الدفع الافتراضية الحالية للرواتب هي `نقدي` لأن نموذج `Payroll` لا يحتوي حقلاً مستقلاً لطريقة الدفع.
- اختبار القبول: راتب مدفوع واحد ينتج سند صرف واحداً، وراتب غير مدفوع لا ينتج سنداً تلقائياً، وراتب الشهر نفسه للمعلم نفسه مرفوض، وصافي راتب سالب مرفوض.

> ملاحظة تشغيلية: إذا فشل إنشاء السند بعد حفظ الراتب بسبب صلاحية أو مشكلة قاعدة بيانات، يجب مراجعة سجل الراتب والسند قبل إعادة المحاولة؛ إعادة المحاولة آمنة ولا تنشئ سنداً مكرراً.
