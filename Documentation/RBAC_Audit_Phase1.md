# تقرير تدقيق RBAC — المرحلة الأولى

## نطاق التدقيق

تم فحص بنية مشروع **SchoolSystem** الحالية، وملفات المشروع، وطبقات `Security` و`Services` و`DataAccess` و`UI`، إضافة إلى ملفات هجرة قاعدة البيانات الموجودة في المستودع. الهدف من هذه المرحلة هو تثبيت خط الأساس قبل إدخال أي تغيير جديد على منطق النظام.

## حالة المستودع

المشروع يعمل على فرع `main`، وتاريخ آخر التعديلات يتضمن إصلاحات القوائم المنسدلة، وتطبيع صلاحيات RBAC القديمة، وتوليد أرقام وكود الفصول والقاعات، وحماية تخزين الصلاحيات. لم تظهر تغييرات محلية غير محفوظة في لحظة التدقيق. المستودع يستهدف **.NET Framework 4.7.2** ويستخدم WinForms مع Krypton Toolkit وطبقات Repository/Service.

## الموجود حاليًا

| المجال | الحالة الحالية | الملاحظة |
|---|---|---|
| الكتالوج المركزي | موجود في `Security/PermissionKeys.cs` | يحتوي على 22 مفتاحًا، أغلبها صلاحيات وحدات بصيغة `*.Manage`، وليس صلاحيات إجراءات منفصلة |
| تطبيع المفاتيح | موجود | يدعم المفاتيح التقنية، أسماء العرض العربية، وبعض المفاتيح القديمة |
| الجلسة الحالية | موجودة في `Security/CurrentUser.cs` | تتحقق من الصلاحية وتدعم `DemandPermission` و`DemandAny` |
| مدير النظام | محمي جزئيًا | تُشتق له الصلاحيات كاملة من الكتالوج، مع منع حذف/تعطيل آخر مدير في مسارات المستخدمين |
| كلمات المرور | Salted PBKDF2 موجود | يوجد ترحيل من كلمات المرور القديمة، لكن سياسة القوة الحالية لا تتجاوز طول 6 أحرف وتحتاج توحيدًا أقوى |
| المستخدمون | جدول واحد مع `RoleName` و`Permissions` نصية | لا توجد طبقة جداول معيارية فعالة للأدوار والصلاحيات والعلاقات |
| القوائم الرئيسية | محمية | `MainForm` يخفي الوحدات ويمنع فتحها عند استدعاء الحدث |
| الخدمات | محمية جزئيًا | معظم الخدمات تستخدم صلاحية واسعة مثل `Students.Manage` أو `Fees.Manage` لكل عمليات الإضافة والتعديل والحذف |
| سجل التدقيق | موجود | يسجل المستخدم والفعل والكيان والرقم والتفاصيل والتاريخ فقط |
| قاعدة البيانات | هجرات متعددة موجودة | توجد جداول تشغيلية كثيرة، لكن هجرة RBAC الحالية لا تنشئ `Roles` أو `Permissions` أو `UserRoles` أو `RolePermissions` |
| RTL | موجود عبر `UIHelper` | يحتاج قبولًا بصريًا فعليًا على Windows بعد التغييرات؛ لا يمكن إثبات التخطيط الكامل من بيئة Linux |

## الفجوات المؤكدة

أول فجوة جوهرية هي أن نظام الصلاحيات الحالي **مركزي من ناحية المفاتيح لكنه غير حبيبي**؛ فالمفتاح الواحد مثل `Students.Manage` يحمي عادةً العرض والإضافة والتعديل والحذف معًا. هذا لا يحقق متطلبات `View/Add/Edit/Delete/Search/Print/Export/Approve/Cancel` لكل وحدة.

الفجوة الثانية هي أن قاعدة البيانات ما زالت تعتمد على العمود النصي المتسلسل `Users.Permissions` واسم الدور النصي `Users.RoleName`. هذا يحافظ على التوافق مع النظام الحالي، لكنه لا يحقق نموذج `Roles → RolePermissions → Permissions` ولا يسمح بإدارة أدوار متعددة للمستخدم بصورة قابلة للتوسع.

الفجوة الثالثة هي أن بعض عمليات التصدير والطباعة تستخدم صلاحية عرض أو إدارة الوحدة نفسها بدل مفتاح مستقل. لذلك لا يمكن حاليًا منع مستخدم من التصدير مع السماح له بالعرض، أو من الطباعة مع السماح له بالتعديل.

الفجوة الرابعة هي أن سجل التدقيق الحالي لا يحتوي على `Module` أو `MachineName` أو `IP`، كما أن النموذج الحالي لا يفرض تمرير `EntityId` في كل عمليات CRUD. توجد حماية من فشل سجل التدقيق في بعض المسارات، لكن التغطية ليست موحدة لكل العمليات.

الفجوة الخامسة هي أن حماية `UserService` ما زالت تعتمد على `Users.Manage` لكل قراءة وإضافة وتعديل وحذف وإدارة أدوار المستخدمين، ولا تفصل بين منع حذف المستخدم ومنع تغيير صلاحياته أو كلمة مروره. كما أن منع تعديل مدير النظام أو منح صلاحية أعلى يحتاج قاعدة مركزية صريحة لا تعتمد على إخفاء الأزرار فقط.

الفجوة السادسة هي أن المشروع يستهدف WinForms على .NET Framework 4.7.2 ويحتوي على مراجع خارجية، ولذلك يمكن تنفيذ الفحوص الثابتة والمنطقية في بيئة Linux، لكن **Build النهائي واختبار RTL البصري وتشغيل SQL Server يجب اعتمادها على جهاز Windows**.

## ملفات التنفيذ الأساسية التي ستُعالج

سيبدأ التدقيق التنفيذي من الملفات التالية، ثم يمتد إلى الخدمات والواجهات حسب الوحدة:

| الأولوية | الملفات | الهدف |
|---|---|---|
| عالية | `Security/PermissionKeys.cs`, `Security/CurrentUser.cs` | إضافة الكتالوج الحبيبي والتوافق مع المفاتيح القديمة وواجهات تحقق واضحة |
| عالية | `Services/UserService.cs`, `DataAccess/UserRepository.cs` | فصل صلاحيات المستخدمين، حماية المدير الأعلى، وتوحيد سياسة كلمة المرور |
| عالية | `MainForm.cs` | ربط ظهور وفتح الوحدات بمفاتيح العرض الفعلية |
| عالية | جميع `Services/*Service.cs` | حماية كل عملية CRUD والتصدير والطباعة من طبقة الخدمة |
| متوسطة | `AuditLogRepository.cs`, `AuditLogService.cs`, `Models/AuditLog.cs` | إضافة سياق الوحدة والجهاز والعنصر وربط التسجيل بالعمليات |
| متوسطة | واجهات `UI/*Form.cs` | تعطيل/إخفاء الأزرار وحماية معالجات الأحداث برسائل عربية واضحة |
| متوسطة | `Databass/*RBAC*.sql` وهجرة جديدة | تطوير قاعدة البيانات دون إنشاء جداول متكررة أو كسر التوافق الحالي |

## حدود هذه المرحلة

لم يتم تنفيذ تعديل وظيفي في هذه المرحلة، ولم يتم الاتصال بقاعدة SQL Server فعلية لأن ملفات المشروع لا تتضمن اتصالًا حيًا قابلًا للتنفيذ من بيئة Linux. تم الاعتماد على الكود والهجرات الموجودة لتحديد الواقع. لا يُعد النظام مكتملًا قبل تنفيذ المراحل اللاحقة ثم بناء المشروع واختباره على Windows.

## قرار الانتقال

الخطوة التالية هي **المرحلة الثانية: تدقيق نموذج RBAC الحالي مقارنةً بالمواصفات وتحديد كتالوج الصلاحيات الحبيبي وخريطة كل وحدة وكل عملية**. بعد تثبيت الخريطة، ستُنفّذ التغييرات على دفعات صغيرة مع Build/فحص ثابت وCommit واضح لكل دفعة.
